# Smart Home Demo

A small full-stack CRUD app for managing smart home devices (lights and plugs): add a device, edit it, toggle it on or off, and delete it.

## Tech stack

| Layer        | Choice                                                          |
| ------------ | --------------------------------------------------------------- |
| Language     | TypeScript throughout                                           |
| Frontend     | React + Vite (single-page app)                                  |
| Routing      | React Router                                                    |
| Server state | TanStack Query                                                  |
| API          | Node.js + Express 5, RESTful                                    |
| Validation   | Zod, shared between client and server                           |
| Database     | PostgreSQL 16 (Docker for local development)                    |
| DB access    | Kysely (type-safe SQL query builder) with its built-in migrator |
| Testing      | Vitest, Supertest, React Testing Library                        |
| Repo         | npm workspaces monorepo                                         |

## Project structure

```
apps/
  client/        React + Vite frontend
  api/        Express REST API
packages/
  shared/     Zod schemas and inferred types used by both apps
docker-compose.yml
tsconfig.base.json
```

## Getting started

### Prerequisites

- Node.js 24 (see `.nvmrc`; run `nvm use`)
- Docker

### Run locally

```bash
npm install
cp apps/api/.env.example apps/api/.env
npm run db:up       # start Postgres in Docker
npm run db:setup    # run migrations and seed sample devices
npm run dev         # start the API (port 3000) and web app together
```

Then open the URL Vite prints (usually http://localhost:5173).

In development, Vite proxies `/api/*` to the API, so the frontend and API share an origin and no CORS configuration is needed.

### Other scripts

```bash
npm test            # run all tests
npm run typecheck   # type-check every workspace
```

## Data model

```ts
type Device = {
    id: number // generated by the database
    deviceType: 'light' | 'plug' // fixed once created
    name: string
    room: string
    status: 'on' | 'off'
    createdAt: string
    updatedAt: string
}
```

## API

All endpoints live under `/api`.

| Method   | Path               | Description                                   | Success |
| -------- | ------------------ | --------------------------------------------- | ------- |
| `GET`    | `/api/health`      | Health check, including database connectivity | `200`   |
| `GET`    | `/api/devices`     | List all devices                              | `200`   |
| `GET`    | `/api/devices/:id` | Get one device                                | `200`   |
| `POST`   | `/api/devices`     | Create a device                               | `201`   |
| `PATCH`  | `/api/devices/:id` | Partially update a device                     | `200`   |
| `DELETE` | `/api/devices/:id` | Delete a device                               | `204`   |

Errors use a consistent shape:

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [] } }
```

| Status | When                                           |
| ------ | ---------------------------------------------- |
| `400`  | Request body fails validation                  |
| `404`  | Device not found                               |
| `409`  | Constraint conflict (e.g. duplicate name)      |
| `500`  | Unexpected error (no internal details exposed) |

## Key decisions

**Monorepo with a shared package.** The API and frontend both import Zod schemas from `packages/shared`, so request and response types can't drift apart. The shared package exports TypeScript source directly to avoid a build step; in production I'd build it (e.g. with `tsup`) or bundle the API.

**Separate schemas per operation.** `CreateDeviceSchema`, `UpdateDeviceSchema` and `DeviceSchema` are distinct, because a create payload has no `id`, an update is partial and can't change `deviceType`, and the response includes timestamps.

**`PATCH` rather than `PUT`.** Users update individual fields (most often `status`) rather than replacing a whole device.

**Postgres over SQLite.** SQLite would remove Docker from the setup, but Postgres reflects how this would run at scale and handles concurrent writes properly.

**Validation at two layers.** Zod validates at the API boundary; the database enforces the same rules with `CHECK` constraints on `device_type` and `status`.

**Database-generated IDs.** Uses `GENERATED ALWAYS AS IDENTITY`. At scale I'd consider UUIDv7 (see below).

**Kysely rather than an ORM.** Queries read like SQL, so it's always clear what runs against the database, while still being fully type-checked against a `Database` interface. There's no ORM abstraction or custom schema language to learn. The trade-off is that migrations are written by hand (with `up` and `down` functions) rather than generated from a schema.

**Repository layer.** Route handlers call a small `devicesRepo` rather than querying the database directly, keeping HTTP concerns separate from data access.

**Express 5.** Chosen for familiarity and because Express 5 forwards errors from async handlers to error middleware. Fastify or Hono would offer stronger built-in typing and validation.

**Auth not implemented.** Out of scope for this task. In production I'd use a managed provider (Auth0, Cognito or Clerk) rather than rolling my own.
